# 从零认识双瓶动作生成器：它怎么规划、为什么这样做、哪些事还做不到

> **一句话结论**：现在做出的是一个**可以在CPU假场景里逐步工作的、在线规则专家的高层动作*提议*生成器**。它不读取以前录好的动作来冒充答案；真实试采分开做过**两个不同seed、各一次**：100022任务成功但仅46次，按H50拒收；100023任务成功59次，验出**同seed的8个H50来源候选**，却仍缺独立验证seed和数据审批，**目前没有获准训练集**。参见[两次真实试采结果](<H50_ONLINE_EXPERT_STRIDE20_S100023_RESULT_ZH.md>)。详见[生成器源码](<../src/online_bottle_expert_actions.py>)、[CPU测试](<../tests/test_online_bottle_expert_actions.py>)与[新seed试采门](<H50_ONLINE_EXPERT_NEWSEED_PLAN_ZH.md>)。

## 先认识四样东西

1. **seed（随机种子）**：给场景的“抽签编号”。同一个seed通常让瓶子从同一种初始摆放开始；不同seed才是另一种场景。本次技术成功用的是已知seed **100013**，随后各只试过一次独立新seed **100022**和**100023**：前者双瓶成功却只有46动作而被H50拒，后者成功59动作并在同一个seed上形成8个未批准的H50来源窗口。同seed重复成功不能当作两名新考生的成绩。
2. **14维动作（14D）**：一张双臂操控指令单：左臂6个关节目标（索引0–5）＋左夹爪开合（索引6）＋右臂6个关节目标（索引7–12）＋右夹爪（索引13）。夹爪在0到1之间，不是14个摄像头、14个力传感器，也不是一次动作只走一个物理步。
3. **物理步**：仿真钟的最小推进单位。原`take_action`接收**一张**14D指令，会在内部用TOPP规划并推进**可变数量**物理步；因此“**H50**”指从同一拍摄时刻起的**连续50次真实高层动作调用**，绝不是50个物理步、50张照片，也不能从旧轨迹每隔25步抽一下就叫50条专家标签。
4. **相机与触觉**：一张照片必须拍在该动作**之前**；输入的触觉只能取同一回合、拍摄时刻**及之前**的过去25物理步。拍完之后产生的接触/任务成功是结果或监督，不能倒灌进此前指令的输入。这叫“因果”，好比考试时不能预看答案。

## 为什么要重新做生成器

原双瓶规则程序能按“**靠近瓶子→抓住→抬起→移向目标**”执行，但它通过`move`/`together_move_to_pose`/`take_dense_action`直接控制逐物理步路径；而VLA策略的入口是`Base_Task.take_action(14D)`。两个接口的“一次动作”单位不同。把旧专家成功视频的逐物理步驱动值随意隔25步抽成64项，会产生**可供新回合试控制的路标**，却不是真专家在同一个相机时刻真实调用`take_action`时给出的指令。[已知seed技术结果](<H50_BOTTLE_CAP8000_V4_RESULT_ZH.md>)确实用这种路标重新控制，第56次调用、6,319物理步碰巧过双瓶目标门；但右瓶y只比阈值内侧约**0.031毫米**，同seed贴边成功不是稳定胜率，更不是新专家训练集。VLA策略自己生成的动作也不能冒充规则专家的纠错答案。

## 新生成器是怎么一步步规划的

想象两名机械臂厨师共同搬瓶。CPU代码 [`online_expert_proposals(task)`](<../src/online_bottle_expert_actions.py>) **必须等外面的执行器拿走上一张指令并真正完成后，才能向后继续取下一张**。它只从当前任务对象读取两瓶、两臂状态与原规则目标，不接受旧回合录像或动作文件。

- **阶段1：抓。** 使用原任务的`grasp_actor`给左右瓶各求“先靠近、再抓住、最后合爪”的阶段任务。双臂动作按阶段配对，不把左臂的夹爪误当右臂。
- **阶段2：抬。** 只有阶段1的指令都已被调用者执行，才向当前机械臂末端请求两侧各向上0.1米的新目标；此时重看**当前**机器人状态，不偷用以前成功回合里“抬完是什么样”的数据。
- **阶段3：送。** 等抬完后，再以**当前瓶位**调用原`place_actor`计算送向左右目标的动作，默认像原任务一样不松开夹爪；不能事先假定瓶子一直牢固握在手里。

对于每个双臂“移动”子阶段，先分别调用原机器人的`left_plan_path/right_plan_path`，规划结果的每行必须恰是**6个有限数**且状态为`Success`。生成器按**本阶段新规划的**路径索引每隔固定25项取一对双臂关节目标，再附上当前左右夹爪位置构成14D；最后一点必取到。路径长短不同用**相同完成比例**配对；抓/松夹爪只输出一条**实测当前关节位置**（不是可能与实测不一致的电机驱动目标）＋新夹爪位置，**绝不重复空动作凑满50**。同一子阶段是一口气规划后分段执行，并**非每个高层动作都重新规划**；下一子阶段才从最新场景重规划。固定25只是便于复现的保守**规划路径索引步长**，没有用新seed优化过，不能把它解释为物理25步或最优控制频率。`MAX_PROPOSALS=128`仅防失控，**不是**成功或训练门。

新增[纯CPU可测试的执行时钟适配器](<../src/online_expert_pilot_executor.py>)会在每张提议前要求同回合照片时间戳等于控制器当前物理步，然后调用原`take_action(qpos)`，记录**实际推进**的起止步数、执行后关节测量与指令最大误差；推进为零、相机错步或照片编号重复都会拒绝，物理上限只能在**不可拆的一次动作后**停止。它只保留内存诊断行，不会写HDF5、签专家成功或许可训练。CPU假场景测试了阶段调用时序：生成器尚未取第一张指令时不会规划；只有“抓”的动作被假执行器逐次执行后才会查询“抬”；“送”的路径从已执行的抬升状态规划。还测试了右臂规划失败、路径NaN、左右配错、夹爪越界及任务提前成功均**拒绝或早停**。这些CPU测试本身不是GPU结果；独立的新seed真实回合已另行实跑并记在[结果报告](<H50_ONLINE_EXPERT_S100022_RESULT_ZH.md>)，不能拿CPU用例的6条当其46条。

## 必须正视的缺陷（不是小字免责）

| 风险 | 为什么重要 | 现在的处理 |
|---|---|---|
| **开环小段会偏** | 阶段中间一次规划、按25个*规划路径索引*取样；它们不是25个真实物理步，TOPP可能耗时不同，抓瓶后滑动或规划旧了都会偏。 | 跨阶段重新看当前场景；阶段内不自动闭环修正。新seed真机仿真若失败必须如实记失败，不调参刷通过。 |
| **双臂不同步/碰撞** | 两边路径长度、关节极限或物体遮挡可能不一样；原规划器`Success`并非安全保证。 | 长度/6D/有限值/夹爪范围和失败状态拒绝；按完成比例配对只是候选，没有完整碰撞或抓力安全证明。 |
| **TOPP可能退化** | 原`take_action`的单侧TOPP失败时会走约50步的回退分支，可能只调夹爪而不移动该臂；调用次数仍会增加。 | 执行适配器会记录**实际关节与指令的差值**供后续审查；一次真实seed100022回合测得最大关节差约0.08306，但尚未按物体/末端设置合格阈值或鉴别每次TOPP回退，不能只看“发出了50条”就称50条有效专家动作。 |
| **阶段/任务成功不等于稳握** | 原双瓶`check_success`只看双瓶功能点xy距离各<0.1米、z>0.89米，**不检验**放下后保持、碰撞、夹力或真硬件安全。 | 成功回合也必须另验接触和轨迹质量；贴边一次不报泛化或安全。 |
| **新seed可能不够50条** | 原任务提前成功、规划失败、重复的放置子目标或不同seed路径长短都可能缩短调用数；纯CPU假场景仅6条是用例，不是H50。 | 不插值、不复制、不凑数；未有≥50连续真实动作＋相机前史就拒H50。先有[“每20个新规划索引取一次”的CPU假设](<H50_ONLINE_STRIDE20_CPU_DESIGN_ZH.md>)，后经单独授权才在**不同**seed100023真实试过，达成59动作/8个相关H50候选窗口；这不证明stride本身带来改进。 |
| **任务成功不等于H50数据** | 真实seed100022已有同回合原始物理5,688步、46次动作及46张拍照前marker，但成功太早：不足50次，故**没有成功completion或专家HDF5**。 | 私有轨迹仅保留负证据；旧seed不能拼接，新seed不可重跑补足，registry仍未批准，具体SHA见[真实试采报告](<H50_ONLINE_EXPERT_S100022_RESULT_ZH.md>)。 |

## 怎么判断以后能不能用于训练

用户已亲自在工作台停GPU并批准**单次seed100022/上限10,000物理步/900秒**；真实回合提前在5,688步/46条动作时成功，**未生成专家HDF5或completion**，这一次资格已经用完。随后用户另批的**新seed100023**显式stride20回合取得59次真实高层动作、59张相机与同回合HDF5，逐SHA和过去25步触觉门验出[8个H50候选窗口](<H50_ONLINE_EXPERT_STRIDE20_S100023_RESULT_ZH.md>)；这是同一seed的8个相关观察，**不等于8个独立专家，也不能把seed100022补步或旧技术路标拼进来**。[H50验收器](<../src/policy_highlevel_chunks.py>)只把合格动作钟列为来源候选，它**还不能直接作为获批训练集**：还得有不同seed的训练/验证数据、训练折归一化、负责人明确审批，才有权接VLA训练forward/optimizer；真实RPC与视觉-only对照是更往后的事。不要把“代码写好了”“单次目标成功”“传感器有力数字”混说成“触觉让VLA变强”。

**本次交付边界**：100022回合46<50真实负结果保留，100023回合59次成功且8个同seed来源候选已有原生HDF5，但**主注册表未批准、validation H50为0、没有GPU触觉adapter训练或真实触觉RPC**；原RoboTwin与旧基线保持不动。
