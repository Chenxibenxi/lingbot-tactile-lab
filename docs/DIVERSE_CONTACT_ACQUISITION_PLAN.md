# Follow-up relay-only diverse-contact/failure collection plan

The first five successful `lift_pot` expert episodes are useful same-run timing examples but all grasp the same task; train-fold next-frame new contact onset has only **one bilateral event per seed**. The owner selected **more contact and failure counterexamples before fitting a model**. No previous LXC/H20 data may become relay training input.

## Bounded second-task pilot

The existing local RoboTwin source's `pick_diverse_bottles` task samples two bottle models (indices 0–19) at varying left/right positions, asks the corresponding arms to grasp, lift, and place both bottles, and checks their final poses. This introduces different contact geometry from a single shared pot. A historic *local evaluation* log records selected seed `100000` as a visual-policy success and seed `100007` as a policy failure, but neither policy result proves what a **new rule-expert rollout** will do on the current relay setup. They are predeclared candidates, **not** cherry-picked proof or a mixed success-rate denominator.

`src/run_expert_relay.sh` and `src/record_expert_demo.py` now allow only the added exact task name alongside their original allowlist; original RoboTwin task files stay read-only. Initially allow **one** new trial ID `relay_pickdiverse_s100000_expert0`, seed100000, bounded 660 s. Before that GPU trial: confirm the service has **no active or queued request and no ongoing generation phase**, acquire the interactive GPU lease, use Strata's own atomic idle unload, stop only its unloaded service, and check no other compute process remains. If any guard fails, do **not** retry by killing processes or switching hosts. On completion or failure, restore Strata to loaded baseline and release lease; inspect source hashes and the exit status.

An expert success can produce a task-specific **unassigned candidate card** only after planner and task goal pass, same-run HDF5/frame/physics observations and hash-bound success/completion gates validate. A planner/task failure is a **separate negative diagnostic**: retain its rejected `failure.json` and telemetry locally, never call it an expert positive, do not force a `completion.json`, do not put it in train/validation/test, and do not treat missing HDF5 as a successful visual negative. The existing planner-failure lift-pot trials remain private diagnostics. One new bottle success would still be **fewer than five independent seeds for that task**, so it cannot enter a bottle train/validation/test split or alter the existing lift-pot pilot split.

## What would make a useful counterexample

Record source roles and seeds independently; count observed left/right finger contact, missing telemetry, first contact and failed/no-contact paths. To test anticipation, acquire controlled near-contact misses and visually similar successes with different outcomes, *without* injecting future object state or force into inputs. Future force is permitted only as an offline target and only after a real executed action interval. A task/task-family split and more varied seeds are required before generalization claims. SAPIEN impulse/dt remains an uncalibrated proxy, not a GelSight observation or a hardware gripper force bound.
